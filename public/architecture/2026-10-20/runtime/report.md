# Runtime and gameplay architecture audit

Commit: `5bf351248de6050876fe5b53f91209a970cc5668` (Civ13/Civ13 master snapshot supplied for this audit). Read-only static analysis. No server, compiler, live client, deployment, publication, or paid service was used. All source links pin this commit. AGENTS.md was read; its operational guidance is not treated as proof of runtime behavior.

## Scope and interpretation

This report covers startup, process scheduling, round phases, human movement/input, item combat/projectiles, crafting, faction research, simple-animal AI, and delayed-action ownership. Mermaid files describe component, class, sequence, and state abstractions. They are not a claim to enumerate every concrete execution trace. Random choices, arbitrary player inputs, map-specific overrides, spawned callbacks, configuration recipes and unlimited repeated rounds make that set unbounded. The accompanying inventory covers the full tracked DM tree.

Evidence labels used below:
- **Proven source edge**: a call or state assignment is present at the cited location.
- **Dynamic edge**: receiver type, hook, callback, map, recipe or registered object determines the implementation at runtime.
- **Unresolved activation**: code is compiled, but an ordinary startup path to running it was not established by this review.
- **Review concern**: architectural risk or stale documentation, not a verified gameplay defect.

## 1. Startup and scheduling ownership

Pre-map `/datum/global_init/New()` creates game ID, reference registries, configuration and chemistry definitions, then deletes itself. Native map construction occurs before `/world/New()`. World startup records compiled dimensions and detects persistence recovery before yielding, runs configuration post-load and startup hooks, builds materials and the shared research registry, creates `/processScheduler`, and schedules setup. The process scheduler is set up before `setup_everything()` initializes occupations, movable atoms, areas, access-list files, recipe files and dictionary data. These are interleaved cooperative operations, not an atomic initialization transaction. ### Scheduler execution contract

1. `start()` installs a new run token, sets interval from `world.tick_lag`, orders processes by priority and spawns the main loop. A replacement start retires the prior sleeping scheduler invocation through token inequality.
2. Each cycle checks running processes, queues enabled idle processes whose game-state and interval gates pass, then relays eligible queued work within a tick-usage envelope.
3. `relayProcess()` has `waitfor = FALSE`; it initializes a missing work snapshot and calls the process wrapper. `started()` marks running, records timestamps and invokes `onStart`; `process()` invokes `fire` unless paused; `finished()` returns idle and keeps only unfinished nonempty budget snapshots.
4. Ordinary priorities copy registered lists and remove visited entries. VERY_HIGH aliases the live list and skips both removal and the ordinary per-process tick check. These macros affect movement/projectile/throwing semantics and must be represented explicitly in performance reasoning.
5. Hung states escalate by elapsed time, then the scheduler constructs a replacement of the old runtime type, copies selected configuration/state, replaces owner maps/list entries and kills the old instance. Disabled/paused/state-gated are distinct from queue/running status.

## 2. Round lifecycle

The live gameticker state variable begins PREGAME. `pregame()` waits on persistence startup hold and exits if the round was restored. It counts down a 90-second lobby under `round_progressing`, with map voting able to wait independently; zero advances to SETTING_UP. `setup()` retries or returns to PREGAME when persistence/save/admission gates do not permit a fresh round. Success sets PLAYING, resets occupations, creates ready characters, collects minds, equips roles, starts time-of-day logic and invokes roundstart hooks. Restored rounds bypass fresh character/equipment/map setup. [code/game/gameticker.dm:6-35](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/gameticker.dm#L6-L35) [code/game/gameticker.dm:45-157](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/gameticker.dm#L45-L157)

Map tick checks faction boundaries, elimination conditions, map-specific win conditions and events; the base win-condition implementation sets `ticker.finished`. Ticker does not run every native tick: the process interval is two seconds. For normal rounds its process transitions PLAYING -> FINISHED and spawns delayed roundend/reboot handling; admin `delay_end`, epoch-swap state and persistence rechecks can alter that path. A persistence-active round clears finished and stays PLAYING. World reboot separately checks save/restart ownership and startup holds before native restart or OpenDream supervisor behavior. [code/game/objects/map_metadata/_map_metadata.dm:477-522](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/map_metadata/_map_metadata.dm#L477-L522) [code/game/objects/map_metadata/_map_metadata.dm:684-735](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/map_metadata/_map_metadata.dm#L684-L735) [code/game/gameticker.dm:193-245](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/gameticker.dm#L193-L245) [code/world.dm:235-277](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/world.dm#L235-L277)

`02_round_lifecycle.mmd` is the gameticker abstraction, not a lifecycle diagram for every map metadata subtype. Map-specific state variables and hooks are dynamic extensions. In particular, a map's `game_over`, victory timer and `ticker.finished` are not universally synonymous.

## 3. Input, movement and collision

Input has native cardinal/diagonal handlers and held-direction start/stop verbs. The delayed mob-construction callback adds a non-lobby client to `movementMachine_clients`; the movement loop selects cardinal or combined diagonal intent, checks movement ownership/delay, then asynchronously calls `client.Move`. It removes the client while movement is busy and re-adds after the current delay. The loop requests a 0.01-second interval but this is not evidence BYOND delivers 100 Hz simulation. ### Shared delayed-action boundary

`do_after` locks ordinary repeated actions, captures actor location, active hand and target location, shows progress, then sleeps and revalidates incapacity/movement/hand/target. It clears the lock and progress at completion. Optional mining context claims and validates actor+turf ownership; gameplay bridge context is conditional on `CIV13_GAMEPLAY_BRIDGE` and must not be flattened into the default signature. ## 4. Combat and polymorphic item interaction

`atom.Click -> usr.ClickOn` is the common mouse entry. ClickOn first checks target and next-click deadline, then routes modifiers, special equipment/vehicle branches, active-hand/self interactions, adjacent versus ranged interaction, or unarmed action. Do not interpret every click as an attack. [code/_onclick/click.dm:7-74](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/_onclick/click.dm#L7-L74) [code/_onclick/click.dm:198-287](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/_onclick/click.dm#L198-L287)

Item dispatch order is explicit: resolve turf attack first when appropriate; then target `attackby`; then item `attack_obj` for objects. A truthy resolved result suppresses ordinary afterattack paths. Living target `attackby` can route surgery; otherwise item `attack` applies eligibility, stamina, logging, cooldown and animation, asks the target to resolve the hit, and invokes `apply_hit_effect -> hit_with_weapon` for a resolved hit. Target/item subclass overrides determine actual armor, hit-zone and special-effect branches. [code/_onclick/item_attack.dm:22-74](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/_onclick/item_attack.dm#L22-L74) [code/_onclick/item_attack.dm:92-121](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/_onclick/item_attack.dm#L92-L121)

Gun `afterattack` routes aiming/PreFire or Fire; Fire uses weapon-specific ammunition acquisition and calls projectile processing/launch. Projectiles register and travel through their own process queue; `process`, `handleTurf`, `attack_mob`, `do_bullet_act` and target `bullet_act` decide collision, miss, penetration and damage. `process/projectile.reset_current_list` limits the current list to 500 and deletes the excess; this is explicit overload behavior, not proof of a measured problem. ## 5. Crafting and research

Recipes have both code-defined variants and config-driven records. Setup reads `config/crafting/material_recipes*` lines containing 13 comma-separated fields into global/faction lists. `material.get_recipes_civs` chooses race/faction and map/civilization research values. Generation resolves result path strings with `text2path`, gates by research-node completion when mapped, otherwise legacy three-axis research thresholds, and applies era/material/feature checks before creating stack-recipe datums. This is a data-to-type construction boundary. [code/setup.dm:83-107](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/setup.dm#L83-L107) [code/game/objects/items/stacks/civ_recipes.dm:19-144](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/items/stacks/civ_recipes.dm#L19-L144)

The stack menu Topic path validates actor state and held source, resolves recipe/sublist/multiplier, and uses `H.can_build_recipe` to serialize the operation. `produce_recipe` is a large content-specific transaction: feature gates, subtype-specific prompts and temporary constructions, derived time, `do_after`, post-wait special revalidation, debit with `use(required,H)`, dynamic `new recipe.result_type` and post-construction configuration. Craft cancellation and payment semantics are branch-specific. In particular, wood-handle crafting keeps the exact handle/source through the wait, revalidates both, and removes the actual equipment slot only after successful main stack debit. Do not generalize that transaction guarantee to every recipe branch without a separate branch audit. [code/game/objects/items/stacks/stack.dm:298-335](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/items/stacks/stack.dm#L298-L335) [code/game/objects/items/stacks/stack.dm:1805-1830](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/items/stacks/stack.dm#L1805-L1830) [code/game/objects/items/stacks/stack.dm:1898-1944](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/items/stacks/stack.dm#L1898-L1944) [code/game/objects/items/stacks/stack.dm:2355-2437](https://github.com/Civ13/Civ13/blob/5bf351248de6050876fe5b53f91209a970cc5668/code/game/objects/items/stacks/stack.dm#L2355-L2437)

## 7. Review concerns and concrete follow-on verification

These are evidence-supported review targets, not asserted bugs:

1. **Mixed scheduler ownership and stale comments.** Included MC/timer infrastructure, legacy process comments naming non-existent grouping owners, deferred-setup record without observed use, spawned loops and native walking create competing mental models. Verify actual startup with a fixture trace of process creation, ticker creation, loop starts and readiness. Do not assume declared controller files are active. Sources: startup/scheduler sections above.
2. **Budget fairness depends on list shape and macros.** Ordinary loops retain work snapshots, VERY_HIGH uses live lists, and research fire iterates a fresh bench copy with a tick check rather than the same current-list resume protocol. Inspect large-list progress and mutation behavior with native tests before claiming fairness/starvation.
